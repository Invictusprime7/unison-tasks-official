# Copilot Instructions for Unison

## Current architecture sources

Use root and directory `AGENTS.md` rules, `docs/ARCHITECTURE.md`, `docs/AGENTIC_IDE.md`, `docs/RESOURCE_RUNTIME.md` and `roadmap.md`. Source-reviewed 2026-10-08. Historical deterministic-only launch plans are evidence, not current authorship policy.

## Protected authority chain

```text
Chat + LauncherWizard (selection only)
  → shared LaunchPlan / launchOrchestrator
  → canonical planning, contracts and sealed Art Direction
  → UnisonAppBuilder isolated application candidate
  → bounded validation/repair and site-wide closure
  → commitMutation / VFSCommitService
  → accepted revision + SiteBundleSnapshot
  → Builder envelope, Live Preview and Playground projections
```

App Builder authors fresh pages; the canonical platform owns topology, routes, capabilities, intents, bindings, Stage 4b tokens, protected infrastructure and acceptance. Do not add a competing deterministic page-body author after candidate authorship. AI/provider failures must not silently replace an accepted or failed candidate with a generic site. Intermediate page and repair attempts are not accepted revisions.

## Authority boundaries

- Persisted revision envelopes outrank launch compatibility and route/browser hints. Reopening accepted projects does not regenerate source.
- SiteBundle composition owns section presence/content/layout; topology owns page identity. Design variation is style-only.
- Generated `/src/App.tsx` is the canonical PageRegistry HashRouter, never AI-authored. The application shell's BrowserRouter is a separate concern.
- Theme families classify sealed Art Direction packs; brand changes do not replace packs or topology. Stage 4b and semantic design tokens remain authoritative.
- Use the attached Unison design system and existing legal vocabulary; compose before inventing. Managed library source is not consumer-editable. Contract-valid local artifacts require provenance and validation.
- Registry projections are derived, never parallel hand-maintained inventories. External design-reference intake has no live dependency in generated sites.
- `commitMutation` is the only canonical source/revision writer. Compilation helpers, agents, terminal and preview cannot persist independently.
- Preview and Playground project source/state; neither owns fallback authorship. Fabric is graphic tooling, not website rendering authority.

## Editing and business data

Builder mutation surfaces use `builderMutationCoordinator` and existing mutation services. Terminal file commands emit FileOps through `onPatch`; host commits inside `runExclusive('terminal')`. Toolbar AI extends AI Builder, sharing conversation, targeting and save checks. Node addresses and section actions are shared with the command menu.

Intent-retarget checks precede AI acceptance. Full Auto bypasses ordinary approval/advisory holds, not authorization, source validation or protected-file checks. Automated older binding/CRM/republish saves cannot replace newer accepted AI edits. Invalid user edits reject without quarantining pages or injecting unrelated intent forms.

`agentOperations` owns migrated catalog operations. Resource Runtime provides shared catalog/content/profile mechanics with separate adapters and lifecycles. Record marks are identity, labels presentation; record writes and Undo are not source checkpoints or cross-storage transactions. No custom hook files.

## Verification and implementation

Trace invoked source ownership before changes. Add focused regression/closure tests where behavior changes; use repository test commands and bypass guards. Source-only tests and historic reports do not establish hosted deployment parity.

Verify real authenticated edit → save → preview → read-back flows before claiming end-to-end completion. Preview load signals and read-only current-route probes are not proof that visitor actions persisted. Local Playwright runs outside the client bundle; hosted worker/candidate preview remains open.

Preserve compatibility until persisted restore and parity tests prove removal safe. Never introduce alternate VFS/snapshot writers, post-seal mutation, label-based bindings, caller-supplied privileges or vertical-specific generation engines. Deployment and schema changes require explicit scope; documentation updates do not imply either occurred.
